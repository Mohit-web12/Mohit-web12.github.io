Pharmacy inventory database

ToolsSQL, Microsoft Access
TeamBuilt with my partner Emon
Result7 tables, 5 queries, data entry forms and a spending report

The question

A pharmacy has to know what's on its shelves, what's about to run out, what has expired, who it buys from, and who it sells to. We wanted one database that could answer all of that, instead of a pile of spreadsheets that drift out of sync.

What we built

We modeled the pharmacy as seven tables and built it in Microsoft Access, with forms for entering customers and medicines, forms that show a sale or order together with its line items, and a report of what each customer has spent.

The seven tables
TableWhat it holdsPoints to
MedicineName, brand, category, price, stock on hand, reorder level, expiry dateSupplier
SupplierName, contact, addressNothing
CustomerName, contact, addressNothing
SaleDate, total, payment methodCustomer
SaleDetailEach medicine in a sale, with quantity and priceSale, Medicine
PurchaseOrderOrder date, expected delivery, total costSupplier
OrderDetailEach medicine on an order, with quantity and costPurchaseOrder, Medicine

Sales and purchase orders each get their own detail table, so one sale or order can hold any number of medicines without repeating the header information. Every medicine points to the supplier that provides it, and every sale points to a customer.

Then we wrote queries for the five questions we set out to answer:

  • Which medicines need to be reordered, because stock fell below the reorder level?
  • How much has each customer spent?
  • Which medicines does each supplier provide?
  • Which medicines have expired and need to come off the shelf?
  • What sells the most, and how many units?
SELECT M.MedicineName, SUM(SD.QuantitySold) AS TotalUnitsSold
FROM (Medicine AS M
      INNER JOIN SaleDetail AS SD
      ON M.MedicineID = SD.MedicineID)
GROUP BY M.MedicineName
ORDER BY SUM(SD.QuantitySold) DESC;

The best sellers query: join every line item to its medicine, then total the units.

What we found

On our sample data, the reorder query flagged two medicines: Vitamin D3, with 40 in stock against a reorder level of 50, and Loratadine, with 35 against 40. The expiry query compares each date with today's date, so it stays correct without anyone editing it.

Splitting each sale and order into a header and line items was what made the useful queries short. Totals per customer and units per medicine are each one join and a GROUP BY.

What I'd do next

  • Track expiry by batch. Right now each medicine has one expiry date, but a real shelf holds several deliveries that expire at different times.
  • Move it to PostgreSQL and enforce rules in the database, like stock that can never go below zero.
  • Turn the reorder query into a draft purchase order, grouped by supplier.
